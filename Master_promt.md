- Команда: соло / 1 человек. Опыт команды не указан в проекте.
- ОС разработки: Windows; целевой клиент: Windows + Linux.
- Хостинг сервера: обычный VPS (Linux, Docker), без облачных кластеров.

## SCOPE: ЖЁСТКИЕ РАМКИ
Цель этапа — вертикальный срез, а не «вся MMO». Разрешено только:
- 1 играбельный класс, 5 способностей, уровни 1–10.
- 1 небольшая зона (~500×500 м), 1 хаб-точка спавна.
- 8–12 мобов двух типов + 1 мини-босс, респавн, лут.
- Инвентарь 20 слотов, 6 слотов экипировки, 15–20 предметов.
- 5 квестов (kill / collect / talk), NPC-диалог, торговец.
- Чат: say / party / system. Группа до 5 человек.
- Персистентность персонажа в PostgreSQL.
- Целевая нагрузка: 50 одновременных игроков на одном процессе сервера.

## АРХИТЕКТУРА: НЕПЕРЕГОВАРИВАЕМЫЕ ПРАВИЛА
1. Сервер авторитарен. Клиент отправляет НАМЕРЕНИЯ (input, request_cast,
   request_loot), никогда — результаты (урон, позиция, предмет, кулдаун).
2. Клиент предсказывает только своё движение. Всё остальное — интерполяция
   снапшотов с буфером ~100 мс. Никакой клиентской логики урона/лута.
3. Одна симуляция движения — общий модуль для клиента и сервера
   (детерминированный, без рендера и без обращения к синглтонам клиента).
4. Композиция нод вместо ECS: HealthComponent, StatsComponent,
   CombatComponent, InventoryComponent — обычные Node-скрипты.
5. Данные отдельно от кода: предметы/способности/мобы/квесты — JSON в
   resources/data/, загружаются реестром на старте. Правки баланса = правки JSON.
6. Сеть: ENet (ENetMultiplayerPeer). Один канал unreliable для снапшотов,
   один reliable для событий. Сериализация — PackedByteArray / var_to_bytes,
   не «сырые RPC со словарями».
7. Сервер headless, без единой ссылки на UI/камеру/Input. Общий код не тянет
   клиентские зависимости.
8. Все клиентские запросы проходят валидацию: тип, размер, частота,
   дистанция, кулдаун, ресурс, состояние, права. Невалидное — отклонить + лог.
9. Никаких магических чисел в геймплейном коде — только из конфигов/JSON.
10. Прежде чем усложнять — спроси, нужно ли это для 50 CCU. Обычно нет.

## ПРАВИЛА КОДА
- Только актуальный Godot 4 API: instantiate(), @export, @onready,
  signal.connect(Callable), create_tween(), CharacterBody3D.velocity +
  move_and_slide(), ResourceLoader.load_threaded_request().
- Никакого Godot 3 API (instance(), yield, connect("sig", obj, "method"),
  KinematicBody, spatial-ноды). Если сомневаешься в API — скажи прямо.
- Статическая типизация везде: var x: int, func f(a: float) -> bool.
- class_name только для переиспользуемых типов; остальное — preload.
- snake_case файлы и функции, PascalName классы/ноды, SCREAMING_SNAKE константы.
- Один скрипт = одна ответственность. Файл > 300 строк — предложи декомпозицию.
- Комментарии объясняют «почему», а не «что». Публичные методы — с docstring.
- Ошибки: assert только для инвариантов dev-сборки; в проде — push_error +
  graceful degradation. Сервер не должен падать из-за одного клиента.
- Никаких print() в бою/тике — только логгер с уровнями и троттлингом.
